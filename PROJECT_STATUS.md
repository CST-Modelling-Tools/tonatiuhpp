### Objective and non-negotiable architecture

- Ship two distinct and permanently named applications: `tonatiuhpp-gui` (Windows `tonatiuhpp-gui.exe`) for interactive use and `tonatiuhpp-cli` (Windows `tonatiuhpp-cli.exe`) for nonvisual scripts, simulation and batch automation. The CLI should not require `--headless`. The GUI must not serve as a second CLI via the legacy `--headless` path after migration.
- Use exactly **one compiled scientific implementation** and shared simulation/scripting services for GUI, CLI and official scientific plugins; no headless-specific duplicate kernel or duplicated physics library. The agreed public library names use `Tonatiuhpp`, not `Tonatiuh` or literal `++`: in particular `TonatiuhppKernel` and `TonatiuhppGuiPresentation`; normalize the other product shared-library names consistently as part of an audited mechanical CMake rename (e.g. `TonatiuhppLibraries` and shared services). Preserve C++ APIs unless a change is essential and explicitly reviewed.
- Keep all presentation-only dependencies in the GUI side (currently `TonatiuhGuiPresentation` exists but the main window still lives in the GUI executable). The standalone CLI/kernel dependency closure must exclude Qt Widgets, Qt PrintSupport, SoQt and the GUI presentation target. QtGui and QtQml may remain for existing non-widget geometry, image, plugin ABI and JavaScript needs: **headless is not synonymous with zero QtGui**.
- **No compatibility executables, launcher aliases, symlinks or old production output names** (`tonatiuhpp.exe`, `tonatiuh.exe` where applicable, or `tonatiuhpp_m5_core_headless.exe`). Explain this intentional breaking change to users, scripts and packagers; do not silently preserve old command names. Remove milestone labels from public executable names and future user-facing entry points.
- On Windows, all GUI, CLI and test executables that depend on the same internal runtime DLLs must run from a **single build runtime directory per configuration**, e.g. `build/bin/Release/`, containing only one build-tree copy of each internal DLL. Put discoverable scientific plugins under the matching runtime's `plugins/<category>/` tree and Qt platform plugins in Qt's expected structure. An external install necessarily has its own deployed copy; the prohibition is on redundant copies within one build configuration, not on installation or configuration isolation.
- Use platform-appropriate conventions for Linux ELF RPATH and macOS `.app` bundles rather than forcing the exact Windows directory tree onto other platforms. Preserve reliable external-prefix installation and native/plugin loading on all three operating systems.
